01 / The starting point

What changed
since the last download?

When new course materials arrived, I wanted to know what had changed and keep the previous version. With separate study sessions for different subjects, an update also needed to leave a clear record for the next task.

I used those needs to define the rules for a private course workflow. The file synchronization component later became a separate, public CLI.

02 / The rules I set

Preserve the source.
Explain the change.

I asked for new materials to be compared with the versions already being used, with original files preserved. Reports needed to distinguish new, unchanged, updated, and failed items.

I also required a clear distinction between downloading a file, updating local study material, and uploading to a study project. The public CLI handles file synchronization; the broader private workflow has additional steps.

My contribution

I set the operating requirements and public scope, and requested improvements to the guide. AI coding tools performed software design, implementation, and testing.

04 / Making it usable

A public tool needs
a usable guide.

I asked for a separate repository that excluded account information and actual lecture materials. The public edition includes a two-file demo that works without a university login.

The first README was too difficult to follow, so I requested a rewrite. It now walks through installation, the offline demo, account setup, output files, and troubleshooting, with PowerShell examples for Windows.

05 / Evidence and scope

What was checked.

A recorded CI run passed 78 tests in each of four environments using synthetic files and simulated API responses. The demo above demonstrates initial collection, unchanged files, and a revised file.

The implementation distinguishes upstream changes from local file damage and preserves valid previous copies. The public edition has not been separately verified against a live university account.
